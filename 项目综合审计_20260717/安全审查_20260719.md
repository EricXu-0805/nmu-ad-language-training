# 南医大语言沟通训练平台安全审查（2026-07-19）

## 1. 结论与适用范围

本轮在**本地未提交工作树**上完成了对象级授权、云数据外发、音频原件、排程回执、前端异步状态和浏览器安全控制的复核。早期确认的 7 组问题以及后续增量红队发现的原子呈现、原子技术暂停、导出删除绑定、异步越界和运维目标暴露问题，均已在当前本地代码中修复并补回归；最新快照的后端测试为 **766/766**，前端为 **pretest 12/12 + 主测试 306/306**，前端 lint/build 通过，当前 Python 环境 `pip check` 未发现依赖关系破损。

这些结果只证明“受控、本地、合成数据工程基线”得到加固，**不等于没有漏洞，不等于生产就绪，也不等于正式研究可入组**。本轮没有访问或修改生产/VPS，没有使用真实凭据、真实受试者数据或真实供应商调用，也没有执行生产迁移。

本轮未取得当前代码快照的真实浏览器证据，未联网查询 Python 漏洞数据库；正式内容、正式研究级 autopilot scope、两类量表 definitions 及其正式结果/工作流、真实 provider、目标设备和伦理审批仍未闭合。因此最终结论仍是：**可作为受控模拟开发与内容冻结基线，不能作为真实受试者正式研究系统交付。**

## 2. 审查方法与验证边界

- 静态复核：认证中间件、集中访问策略、场次/音频/attempt 对象授权、云授权撤回与供应商调用顺序、上传流与文件发布、TTS 下载、前端建档与量表抽屉异步状态、modal 键盘边界。
- 自动回归：最新后端全量 `pytest -q` **766/766**；前端 pretest **12/12**、主测试 **306/306**，lint/build 通过。本文各缺陷小节保留其发现当时的定向计数，最终交付证据以第 7 节为准。
- 依赖一致性：当前 `.venv` 的 `pip check` 返回 `No broken requirements found`。这只检查安装关系，不查询 CVE/OSV 等在线漏洞库。
- 明确排除：公网/生产、真实账号与真实数据、真实 API Key、供应商网络调用、目标老人端设备、在线 advisory 扫描和当前代码的浏览器截图。

## 3. 已确认并修复的问题

### SEC-01 高：云授权撤回与实际供应商调用之间存在 TOCTOU

**影响。** 若授权检查和网络发送不是同一个可串行化边界，研究者可能先收到“撤回成功”，而旧请求随后才开始发送音频或回答文本；ASR 的授权也可能被错误复用于后续 LLM 阶段。

**修复。**

- `app/cloud_processing.py:21-48` 为每个受试者建立固定条带的进程内外发锁，不保存受试者标识，也不会形成无限增长的锁表。
- `app/main.py:1048-1053`、`app/main.py:1325-1331` 让研究撤回、云授权 grant/revoke 与外发使用同一把受试者锁，并统一“受试者锁 → 数据库治理锁”的顺序。
- `app/main.py:6911-6946` 在真正调用 cloud provider 前，以 `Session -> Patient` 行锁重新读取场次绑定和当前授权，并把锁保持到 provider 返回后；跨 worker 使用数据库行锁，SQLite/单进程使用同一受试者锁。
- `app/main.py:7391-7405` 与 `app/main.py:7448-7481` 分别在 ASR、LLM 两个独立外发边界前重新授权，拒绝复用较早的 ASR 授权快照。

**验证。** `tests/test_cloud_processing_consent.py:347-409` 覆盖在途 ASR 与撤回的总顺序；`tests/test_cloud_processing_consent.py:412-460` 证明撤回先提交时 provider 调用数为 0；`tests/test_cloud_processing_consent.py:463-522` 证明本地 ASR 后、云 LLM 前撤回时 LLM 调用数为 0，provider 结果不能进入最终判类。

### SEC-02 高：跨账号音频存在性泄露与孤儿音频写入

**影响。** 外账号若能从 foreign/missing 的不同 403/404/409 响应推断音频 id、撤回状态或准入状态，就形成对象存在性 oracle；具名账号若能向无场次的模拟音频资产写入字节，则可能把受保护部署当成任意原声存储槽。

**修复。**

- `app/main.py:2768-2791` 在暴露撤回、完整性、分类或文件状态前先核验音频所属场次与 operator；foreign、orphan、missing 对未授权研究员统一返回 `404 音频不存在`。
- `app/main.py:2794-2845` 将上传权限收紧为：受试者设备只能写精确绑定场次的资产；具名账号必须通过关联场次 owner/admin 策略，不能写无场次资产；开放 M0 仅保留回环本机兼容。
- `app/main.py:2888-2900` 在读取请求体前完成初始对象授权和 VisitPlan 准入；`app/main.py:3000-3018` 在慢上传结束后重新锁定并核验资产、场次、capability 和终态，避免上传期间的切场/撤回 TOCTOU。

**验证。** `tests/test_access_policy.py:916-1077` 同时比较 foreign/orphan/missing 的元数据、blob 读取和 blob 写入，验证完全相同的 404，并验证没有 checksum/byte_count 被写入；`tests/test_access_policy.py:1202-1337` 保留 owner 与终态 data steward 的授权读、外研究员的统一隐藏以及 owner 的 immutable ACK 恢复合同。

### SEC-03 高：started VisitPlan 回执泄露场次绑定

**影响。** 排程本身是单课题组共享事实，但 started 计划若向非场次 owner 下发 `session_id` 或 `started_by`，会把共享排程变成另一个研究员场次对象的索引，绕过场次详情路由的存在性隐藏。

**修复。**

- `app/visit_plan_service.py:238-254` 对 started 回执按 viewer 投影：owner、admin 与回环 M0 保留完整回执；其他具名团队角色看到排程状态与时间，但 `session_id`、`started_by` 被清空。
- `app/main.py:1595-1642` 把 viewer actor/role 显式传给今日队列和按患者列表。
- `app/visit_plan_service.py:797-868` 的今日床旁队列只返回当前仍合规的 `approved` 计划，不返回 started 绑定；`app/visit_plan_service.py:872-907` 的患者计划列表统一使用 viewer 投影。

**验证。** `tests/test_visit_plans.py:201-283` 验证 owner/admin 可见完整 started 绑定，另一研究员/data steward 只见排程且 `session_id`、`started_by` 为 null，并验证 today 只含 approved 行。

**明确的产品边界。** `created_by`、`approved_by` 是启动前共享 scheduling provenance，在当前“一个部署工作区对应一个获批课题组”的模型内继续对具名团队可见；它们不是场次 owner 授权，也不能用于读取 Session。若未来一个部署混入不同课题或站点，必须先新增 Study/Membership/PatientAssignment ACL，不能沿用当前共享模型。

### SEC-04 高：owner 检查晚于准入/运行态诊断

**影响。** foreign 历史/孤儿场次若先经过 VisitPlan 准入、当前 live slot、runtime 或 autopilot 状态检查，再做 owner 授权，攻击者可利用 `404` 与具体 `409` 的差异推断场次存在和内部状态。

**修复。**

- `app/main.py:210-234` 新增统一 `_load_session_for_operator`：只解析对象并先完成 owner/data steward/admin 授权，不在 helper 内暴露任何准入或运行态诊断。
- `app/main.py:3541-3563` 的 live payload 先做对象授权，再比较当前 live slot，最后才检查 started VisitPlan。
- `app/main.py:3842-3905` 的 session handshake、cursor/rapport 写入先通过 owner-first helper；`app/main.py:2343-2368` 的录音授权与 runtime、finish、closeout、complete、abort、autopilot start/takeover 等写路径也统一为“对象授权在先，状态诊断在后”。

**验证。** `tests/test_access_policy.py:916-1077` 对 8 组历史场次 mutation、live session/cursor、音频读写逐一比较 foreign 与 missing：未授权者得到同一 generic 404；精确 owner 仍得到真实的 `session_visit_plan_admission_required` 409，不会因隐藏修复被错误放行。

### SEC-05 高：全局 evidence id 可作为跨研究员 oracle

**影响。** `raw_audio_id`、`AttemptEvent.id` 和 source attempt 是全局标识。若在确认它们属于已授权 session/item 前返回 processing status、角色或 mismatch 细节，另一研究员可枚举对象并获知私有处理状态。

**修复。**

- `app/main.py:6319-6329` 在读取 source attempt 的状态/角色前先验证它存在且属于已授权 Item/Session，foreign 与 missing 统一为 `404 source attempt 不存在`。
- `app/main.py:7238-7251` 在任何音频诊断前验证资产属于请求路径中的已授权 session，foreign 与 missing 统一为 `404 音频资产不存在`。
- `app/main.py:7684-7687` 在读取 attempt 细节前验证 attempt 归属当前 session，foreign 与 missing 统一为 `404 attempt 不存在`。

**验证。** `tests/test_access_policy.py:1080-1199` 由研究员 B 在自己的合法场次中分别提交研究员 A 的音频/attempt 与不存在 id，三类入口的状态码和响应体完全一致，且响应不包含对方的私有 error code。

### SEC-06 高：建档 409 慢请求使用了可变表单状态

**影响。** 原建档请求等待期间，用户可继续编辑受试者编号、录音授权或云处理选择；若 409 分支重新读取当前 React 草稿，重复档案核对的可能不是实际已提交内容，造成授权误配、错误沿用档案或错误创建后续训练安排。

**修复。**

- `web/src/console/patientIntakeDuplicate.ts:35-39` 在发请求前复制并规范化不可变提交快照。
- `web/src/console/PatientIntakeScreen.tsx:65-107` 的 create、云授权写入、成功跳转和 409 核对全部使用同一 `submitted` 快照。
- `web/src/console/PatientIntakeScreen.tsx:136-225` 在沿用既有档案或独立修改云授权前重新读取服务器 Patient/policy，任何治理 revision、撤回或告知版本变化均停止并要求重新核对。
- `web/src/console/PatientIntakeScreen.tsx:248-253` 在请求期间禁用建档编辑区；`web/src/console/PatientIntakeScreen.tsx:390-430` 让独立重复档案复核区不被 fieldset 结构误伤，同时在复核请求进行时禁用所有动作。

**验证。** `web/src/console/cloudProcessingPolicy.test.ts:12-52` 模拟快照后继续修改草稿，证明已提交数据不变化，并以源码合同固定 409 使用 `submitted`、busy fieldset 边界和复核按钮禁用。

### SEC-07 中：量表抽屉旧响应覆盖与键盘焦点逃逸

**影响。** 同一受试者重试、快速切换/关闭抽屉时，较慢旧响应可能覆盖最新状态；服务端若意外返回其他受试者行，前端可能错误展示。焦点陷阱若遗漏原生 `<summary>`，键盘用户可从 modal 内的可操作元素跳出，影响床旁可用性和误操作防护。

**修复。**

- `web/src/console/scaleDrawerRefresh.ts:14-31` 以单调 generation 接受最新请求，close/effect cleanup 使在途代次失效。
- `web/src/console/scaleDrawerRefresh.ts:34-43` 对整批 `ScaleResult.patient_id` 做 fail-closed 校验，发现任一跨患者行即整批拒绝。
- `web/src/console/ScaleDrawer.tsx:25-59` 同时检查 generation、当前 patient 和 open 状态后才写入 React state。
- `web/src/components/useDialogFocusTrap.ts:3-11` 把原生 `summary` 纳入共同 focusable selector，Tab/Escape/返回焦点继续由共享 trap 管理。

**验证。** `web/src/console/scaleProtocol.test.ts:31-55` 覆盖同患者旧重试、患者切换、关闭取消和混合患者行；`web/src/components/dialogAccessibility.test.ts:9-24` 固定 ScaleDrawer 使用共享焦点陷阱且 selector 包含 `summary`。

## 4. 当前已存在且复核通过的安全控制

### 4.1 认证、角色与请求防伪

- `app/main.py:286-302`：未启用认证的 M0 只允许本机回环；受保护部署进入账号/PIN/capability 模型。
- `app/main.py:313-335`、`app/main.py:410-500`：PIN 只在设备配对端点比较并限速；老人端使用短时、单场次 capability，不能用 PIN 直接访问 DEVICE 路由。
- `app/main.py:337-408`：具名账号会话按集中 route role 校验；非安全方法要求与 HttpOnly session 绑定的 CSRF proof，浏览器显式非 same-origin 请求在解析凭据前拒绝。
- `app/main.py:557-580`：session cookie 为 HttpOnly、Secure（HTTPS/显式生产配置）、Lax；CSRF cookie 为 host-only、Strict，值是 session token 的 HMAC 派生证明而不是 bearer 本身。
- `tests/test_auth.py:284-310`：缺失/错误 CSRF 与 `Sec-Fetch-Site: same-site` 均拒绝，只有同源且 proof 正确的写请求放行。

### 4.2 Host、浏览器响应头与缓存

- `app/http_security.py:8-20`：应用直连和反代路径均设置 CSP、`frame-ancestors 'none'`、X-Frame-Options DENY、nosniff、no-referrer、Permissions-Policy 和 same-origin CORP。
- `app/http_security.py:23-40`、`app/main.py:513-532`：生产可配置精确 Host allowlist，受保护响应统一 `private, no-store`。
- `tests/test_http_security.py:4-20` 与 `tests/test_auth.py:256-266`：覆盖子域/后缀绕过、空 Host、安全响应头和拒绝响应仍带安全头。

### 4.3 音频原件与资源边界

- `app/audio_store.py:21-32`：raw id 仅允许安全字符，单 blob 硬上限 64 MiB。
- `app/audio_store.py:272-321`：上传以常量内存流式写入隐藏 pending 文件，权限 0600，校验实际字节上限、MIME 容器签名、SHA-256，并在异常时清理。
- `app/main.py:2945-2968`：先检查 Content-Length 和配额，再结束慢请求持有的 SQLite 读事务；`app/main.py:3000-3074` 发布前重新读取全部可变治理事实，校验物理原件与数据库一致后才提交。
- `app/main.py:3111-3133`：原声读取要求具名角色、对象授权和当前治理门禁，响应 no-store，禁用 Range 分段读取。

### 4.4 TTS 外发与 SSRF 防护

- `app/tts.py:3-7`：发送给云 TTS 的文本必须属于冻结内容/固定 UI 闭集，不携带患者字段；白名单外 fail-closed。
- `app/tts.py:41-64`：下载只允许阿里云允许后缀的 HTTPS 443 地址，拒绝 URL 凭据和解析到任何非公网 IP 的域名。
- `app/tts.py:67-104`：禁止自动重定向并复核最终 URL，限制 16 MiB，校验 Content-Type、Content-Length 和 RIFF/WAVE 签名后才允许进入缓存。

### 4.5 部署最小权限

- `Dockerfile:33-49`：运行容器使用非 root 用户；部署约束为单 worker，以保证当前进程内限速器/锁模型的一致性；关闭原始 URL access log，研究动作进入应用内审计账本。
- `requirements-deploy.txt:1-10`：直接生产依赖使用精确版本钉住，当前 `.venv` 的 `pip check` 无破损依赖。
