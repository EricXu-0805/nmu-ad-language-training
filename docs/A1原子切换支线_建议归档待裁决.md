## 1. 这条支线是什么

2026-08-10 至 08-12，收据 186–207 共二十余份设计稿（单份最大 104 KB），目标是造一套
"抗 SIGKILL / 抗主机重启 / 抗 systemd 自动拉起"的原子发布切换机制：一个持久守卫进程
（persistent guard）+ 两级提交（私有内容提交 / 公网最终提交）+ 独立服务授权状态机。

**至今零代码上线。** 最新一份（207）自己写着 `implementation_ready=false`、
`candidate_build_authorized=false`、`host_verifier_executable=false`。
上一版候选（R1）经三路独立审查判 NO-GO，随后被安全退役为不可激活的设计样本
（`RETIRED_FROM_ACTIVATION=true`，收据 190–192）。

## 2. 为什么现在停止投入

- 它要保护的目标是**发布切换过程中的崩溃**。当前这台服务器**没有任何真实受试者数据**
  （1 个虚构受试者、1 个场次、0 条云语音使用记录），有每日快照、异地副本、每周恢复演练
  和历次上线前的回滚存档。这个场景下，崩溃的代价是"重来一次"，不是"数据损坏"。
- 它**不在关键路径上**。距离"养老院能开始用"，卡住的是内容冻结、伦理批件、隐私评估、
  真机验收和养老院接收——没有一项与发布切换的原子性有关。
- 两天写了二十余份设计稿而零上线，本身就是这条路线投入产出比的证据。

## 3. 它识别出的真问题（**仍然成立，不因为归档而消失**）

### 3.1 当前 systemd 单元没有任何事务闸

事实（收据 189 §1，本文核对时仍然成立）：`nmu.service` 与 `nmu-caddy.service` 都是
`Restart=always`，且**没有** `Requires=` / `BindsTo=` / 任何持续守卫。

后果：如果一次发布在同步文件的中途被打断（进程被杀、主机重启、systemd 自动拉起），
systemd 会**把一个半同步的版本重新拉起来并继续对公网提供服务**。

**这一条现在有一个便宜得多的缓解**：本轮实现的 U4——`nmu.service` 增加
`ExecStartPre`，起服前强制核对数据库结构版本，不一致就拒绝起服。
半同步的树几乎必然带来结构版本不一致，因此这道闸把"公开半切换版本"这个最坏情况
挡掉了绝大部分。它不是原子切换，但它是**同一个风险的 80% 覆盖，成本是一行 unit 配置**。

**仍未覆盖的残余**：如果被打断的同步恰好没有改变数据库结构版本（例如纯前端资源更新），
`ExecStartPre` 拦不住。这一条是真的残余，写在这里备查。

### 3.2 一个已被证否的设计模型（别再走回去）

旧设计同时要求"intent 非 COMMITTED 时 Caddy 必须停止"和"intent 仍非 COMMITTED 时先启动
Caddy 完成公网稳定性验证再写 COMMITTED"。这两条**无法同时成立**：放宽前者会公开半切换
版本，坚持前者则后者永远执行不到。

结论：**"单一 COMMITTED 状态同时承担私有文件提交与公网最终放行"这个模型是错的**。
将来若重启这条支线，起点应该是两级提交 + 独立的服务授权状态机（收据 189 的方向），
而不是从 160/162/186 的行动顺序继续。

### 3.3 R1 候选只能当反例

R1 那两个脚本里的历史状态机、rollback、adjudicate 和授权账本，经三路审查判为
**不得复用为将来执行基础**，只能作为只读设计素材。它们已被封死模块级副作用并标记退役。

## 4. 重新启动这条支线的条件

满足任一条，就值得重新评估：

1. 这台服务器开始承载**真实受试者数据**；
2. 发布频率高到人工维护窗口不可持续；
3. 迁到医院内网、由医院信息中心要求可证明的原子发布；
4. 出现一次真实的"半切换版本被公开"事故。

在此之前，发布走 `docs/上线runbook_受控技术环境更新.md` 的逐条人工步骤，
并靠 U4 那道起服前的结构闸兜底。
