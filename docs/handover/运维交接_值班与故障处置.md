# 运维交接：值班、日常检查与故障处置

> 面向接手这套系统日常运维的人。假设你没读过这个仓库的任何代码。
> 本文面向已实际核验的 **systemd 裸机拓扑**。2026-09-07 的应用、库头、备份、入口和调度状态统一读取 [部署状态索引](../RELEASE_STATE.md)；旧日期的状态、配置和数量不作实时事实。目标 Compose 方案见 [部署手册](../../DEPLOY.md)，尚不能套用到未迁移的现役机器。

## 0. 一句话

服务器上跑着一个 FastAPI 应用（systemd 单元 `nmu`）和一个只管 443 的 Caddy（`nmu-caddy`），
外加下表的六个定时任务：每日备份、备份健康检查、容量检查、每周恢复演练、每周 OS 补丁积压检查和公网健康检查。
备份成功以备份日志与对应快照验证为准；服务、恢复演练和安全补丁需要各自日志，不能用备份成功证明整个平台正常。

## 1. 每天只需要看一件事

```bash
ssh root@<服务器地址>
tail -3 /opt/nmu/backups/backup.log
```

最后一行必须是 `ok`，且时间在 30 小时以内。例如：

```
[2026-08-12 19:35:54] ok snapshot=20260812-193551 size=1.2M config=ok keep=14 ...
```

**看到 `FAIL` 或最后一行超过 30 小时没更新 → 按第 5 节处置。**

日志里的时间是 UTC。备份定时器在 UTC 19:30 触发（= 上海时间次日 03:30），
带最多 10 分钟随机延迟，所以时间戳通常是 19:3x。

### 1.1 `systemctl --failed` 里那条常驻的 `networking.service`，忽略它

```
● networking.service   loaded failed failed   Raise network interfaces
```

2026-04-29 开机那一刻留下的：这台机器只有 `eth0`，而系统配置里还写着 `eth1`，
`ifup: failed to bring up eth1` → 单元退 1。**网络本身是好的**（`ip -brief addr`
能看到 `eth0 UP 89.208.253.119/22`，ssh 和 https 都通），四个多月没再动过。

**不要去"修"它**——改远程机器的网络配置，失手就是失联，而它没有任何实际影响。

但要记住这条的存在方式：`systemctl --failed` 从此永远不是空表。
**除它以外的任何一条都要当真**，别因为"这张表本来就有东西"而整张忽略。
它也不会触发告警（没有 `OnFailure`，而且只在开机时失败过一次）。

## 2. 六个定时任务是什么、什么时候跑

```bash
systemctl list-timers 'nmu*' --no-pager
```

| 单元 | 时间（上海） | 干什么 | 失败会怎样 |
| --- | --- | --- | --- |
| `nmu-backup.timer` | 每天 03:30 | 在线快照数据库 + 音频 + 导出，落 `/opt/nmu/backups/daily/`，留 14 份 | 写 `FAIL` 进 backup.log，并触发告警 |
| `nmu-backup-health.timer` | 每天 04:40 | 复核上一次备份是否真的可用，写 `health.state` | 同上 |
| `nmu-capacity.timer` | 每天 05:10 | 磁盘水位与增长速度，写 `capacity.state` | 同上 |
| `nmu-restore-drill.timer` | 每周一 05:30 | 将快照隔离恢复并验证应用启动，写 `restore-drill.state`；新版已在 Linux 实际执行隔离启动，旧版本未运行生命周期的 `ok` 不能据此改标为真正恢复 | 同上 |
| `nmu-os-security.timer` | 每周二 05:50 | 数 apt 安全补丁积压，写 `os-security.state` | 同上 |
| `nmu-health.timer` | 每 10 分钟 | 打一次公网 `/health`（2026-08-28 新增） | 同上 |

2026-09-07 收尾已将六个定时器恢复到维护前启用状态，Mac 原异地调度也已重新加载。`nmu-os-security.service` 的 2026-08-31 失败状态按历史事实保留，未用清除状态来制造全绿；对应定时器已恢复等待下一次计划运行。新头备份和异地副本的本次验证不代替将来的定时执行结果。

**这六个单元全部 `Persistent=true`**：停掉定时器不是取消，是推迟——重新启用的那一刻，
错过的那次会**立刻补跑**。做维护时要记住这一点（见第 6 节）。

失败会通过 `OnFailure=nmu-alert@…` 发到 Discord `#daily` 频道。**只有失败才响**；
"一整天没动静"既可能是一切正常，也可能是告警链本身坏了——所以第 1 节那条命令还是要每天看。

## 3. 三个状态文件（比日志更快看出健康度）

```bash
cat /opt/nmu/backups/health.state       # 期望：HEALTHY
cat /opt/nmu/backups/capacity.state     # 期望：HEALTHY used=xx% free=xxxxMB
cat /opt/nmu/backups/restore-drill.state  # 期望：恢复演练通过：<快照号>
cat /opt/nmu/backups/os-security.state    # 期望：security_pending 为 0
```

## 4. 异地副本（在一台 Mac 上）

服务器上的备份只是第一份。第二份由一台 Mac 每天自动拉走，存在
`~/Library/nmu-backup/offsite/`，由 launchd 任务 `com.nmu.vps-backup-pull` 触发。

```bash
tail -5 ~/Library/nmu-backup/offsite/pull.log     # 最后一行应是 ok snapshots=N ...
ls ~/Library/nmu-backup/offsite/daily | tail -3   # 最新快照号应与服务器一致
ls ~/Library/nmu-backup/offsite/conflicts         # 必须是空的
```

**`conflicts/` 非空 = 有快照的内容和服务器对不上，立即停止并找负责人**，不要自己删。

`legacy-unvalidated/` 里有东西是**正常的**：每次数据库结构升级后，升级之前拍的旧快照
就不再能被新校验器背书，会被移到这里等人处置。它们不是坏备份，但**绝不能改名当成
当前合格快照使用**。

## 5. 出问题怎么办

### 5.1 backup.log 出现 FAIL

1. 先看失败码：`tail -20 /opt/nmu/backups/backup.log`
2. 磁盘满（`df -h /` 剩余很少）→ 先盘点当前占用，按 [部署状态索引](../RELEASE_STATE.md) 核对须保留的旧完整树、匹配快照、校验器与新证据，再由负责人确定清理对象。
   2026-08-20 的旧 tar 曾被列作优先清理对象；那条历史路径和大小不能作为今天直接删除的依据。
   **不要按「保留最近 3 份」删存档，也不要手工删 `/opt/nmu/backups/daily/`。**
3. 其他原因 → 记录原文，找负责人。**不要手工造一份"看起来正常"的快照。**

### 5.2 网站打不开

```bash
systemctl status nmu nmu-caddy
journalctl -u nmu -n 50 --no-pager
curl -sS -o /dev/null -w '%{http_code}\n' https://<站点地址>/health   # 期望 200
```

如果 `nmu` 反复重启，最常见的原因是**数据库结构与代码不匹配**——应用启动前的检查会
拒绝起服，这是设计好的保护，不是故障。这种情况**不要绕过检查**，找负责人。

2026-08-28 起 `nmu` 与 `nmu-caddy` 显式配了 `StartLimitIntervalSec=120` / `StartLimitBurst=5`：
连拉 5 次仍失败就**停止重试、进入 failed**，Discord 收到告警。在此之前 `RestartSec=3`
配 systemd 默认的「10 秒 5 次」永远够不到上限，单元于是永不进 failed，`OnFailure` 一次
没响过——一棵只同步了一半的树会无限重启而全程安静。代价是修好之后它不会自己起来：

```bash
systemctl reset-failed nmu && systemctl start nmu
```

### 5.3 需要回滚到上一个版本

**先判断是哪一种回滚。**

**同结构回滚（绝大多数情况）**：目标版本与当前库头是同一个 alembic head。
以 [部署状态索引](../RELEASE_STATE.md) 对应发布记录选定旧提交与构建产物，先在隔离候选树验证完整文件集、库头与启动。不能假定磁盘上的「最新 tar」就是上一个版本，也不能直接对运行目录覆盖同步。

**跨结构回滚**：目标版本的库头与当前不同。必须**代码树、备份校验器、快照三者一起回**，
并且**绝不执行数据库降级**（`alembic downgrade` 会 drop 表）。本轮已保留与发布匹配的旧完整应用树、旧数据及旧头备份；正常入口开放或异地锚点推进后，必须先核对新增写入与审计边界，不能自动恢复旧业务数据库。现役裸机的具体边界见 [本轮迁移与发布核验](../audits/2026-09-06-migration-and-release.md)，不套用目标 Compose 卷切换命令。

⚠️ **用 `app-before-deploy-*.tar.gz` 之前必须先核对它配不配当前的库。**
2026-08-31 的历史 tar `app-before-deploy-20260831-183746.tar.gz` 对应 `a986f54` / `c8e5a1f3b209`，不代表本轮保留对象，也不能直接替换当前版本。具体对象须按发布索引和现场收据核对。检查时显式指定隔离副本数据库，不能让候选树自动选错库：

```bash
# 先按快照对应版本的验证器检查并解到独立候选目录；禁止在运行目录解包。
cd <隔离候选代码目录>
DATABASE_URL=sqlite:////<隔离候选数据库绝对路径> /opt/nmu/venv/bin/python -I scripts/check_database_head.py
# 退出码 0 才准换上；非 0 说明这棵树与当前库结构对不上，换上去起不来
```

没做过的人不要临场发挥，找负责人。

### 5.4 谁都登不进去 / 平板配不上，提示「尝试过多，暂时锁定」

返回体里的 code 是 `auth_locked`，来自全局失败限速器：同一类操作（登录 `login`、
配对 `pair`）5 分钟内累计失败 64 次锁一次；连续再打满按 **30 秒 → 2 分钟 → 10 分钟
→ 1 小时** 逐级加码，安静 10 分钟以上退回第一档。

先判是不是自己人打出来的——**换过 CONSOLE_PIN 之后旧配对码全部作废**，几台平板同时
重试很容易把 `pair` 那一档打满。确认不是外部在猜密码的话，两条路：

- **等**：最长 1 小时，到点自动解。
- **立刻清掉**：`systemctl restart nmu`（限速器是进程内状态，重启即清零）。
  ⚠️ 正在训练的场次会被中断，先确认没人在用。

阈值在 `.env` 的 `AUTH_GLOBAL_FAIL_MAX` / `AUTH_GLOBAL_LOCK_SECONDS`。调之前想清楚
它在防什么：老人端配对码受这道限速闸保护；码长和轮换记录按密钥制度及注明日期的发布记录核对，不在交接文档中写现役值。

## 6. 做维护前必须知道的四件事

1. **停定时器 = 推迟，不是取消。** 重新 `systemctl start`/`enable` 的瞬间，错过的那次会立刻补跑。
   所以恢复定时器之前，代码、数据库结构、异地校验器、最新快照必须已经互相一致。
2. **这台机器内存很小（1 GiB）。** 恢复演练会临时再起一个应用实例，**必须在主服务停掉的
   窗口里做**，否则两个实例一起吃内存。
3. **不要重启 sing-box。** 这台机器同时是某些设备的网络上游，重启它会把你自己的 SSH 连接
   一起切断。真要动，先用 `nohup` 脱离当前会话。
4. **`/opt/nmu/last-deploy.state` 是索引，不能独立证明部署版本。** 它在 2026-08-17 曾过期，8 月 20 日起的部署记录已经补写，8 月 27 日曾与实测一致；本轮再次发现索引仍为旧提交，现已保留旧索引并登记实际应用提交 `5684a3a`，新索引与本次应用发布收据对应。判断实际运行版本须把完整发布文件集、前端构件、库头和索引绑定到同一候选：

   ```bash
   # 使用修复后验证器生成完整清单；旧版只量 app/scripts Python 的清单不再合格。
   # 打印只读命令，拿到目标机上运行，输出存为 observed.json。
   scripts/verify_deployed_tree.py --print-remote-command --tree-root /opt/nmu/app
   # 回仓库比对；0=一致 1=有漂移 2=根本没量成
   python -I -B scripts/verify_deployed_tree.py --manifest observed.json \
     --revision <候选提交> \
     --expected-dist-manifest <独立受控构建归档>/browser-dist-sha256.json
   ```

   退出码 2 单独分出来是有原因的：「没量成」和「量到了没差别」看起来太像，
   而把前者读成后者，就会得出"生产干净"的错误结论。

   本轮已部署新脚本并在目标环境取得完整源码与独立网页产物的比对证据，见 [修复进度与验收](../audits/2026-09-06-fix-progress.md)。后续发布仍须重新采集并绑定该次应用提交，不能沿用本轮清单。
   构建清单必须独立来自受控构建归档，不能取目标机上同一份自描述清单当作可信参照。新格式为 `nmu.source-release-tree.v1` JSON；旧两列清单只供阅读历史，不再构成整包一致证明。该工具验证源码部署树，不替代镜像签名、秘密配置或真实数据验收。

## 7. 不要做的事

- 不要在生产机上 `pip install`、重建 venv、现场编译。
- 不要手工改数据库。
- 不要为了让检查变绿而修改检查脚本。
- 不要删 `legacy-unvalidated/` 或 `conflicts/` 里的任何东西。
- 不要把测试或本机检查的绿色结果，当成"可以给真实老人使用"的证据——那是另一套门槛，
  见 `docs/handover/七道门现状表.md`。
